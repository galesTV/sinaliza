# AGENTS.md — Sinaliza

Instructions for AI coding agents working on this repository. Read this file before changing anything. App-level instructions may also exist (see `apps/landing/AGENTS.md`, which is auto-generated by `next dev` — do not remove its managed block).

## 1. Project identity

**Sinaliza** is a Brazilian Sign Language (Libras) learning platform built for HackBrasil 2026.

Tagline: *Aprender Libras. Praticar. Evoluir.*

The goal is to make Libras learning more accessible, engaging, structured, and interactive by combining educational content, practical exercises, progress tracking, gamification, and experimental computer vision. The experience is inspired by the engagement/progression systems of platforms like Duolingo, but with its own visual identity and educational approach.

**Hard deadline:** November 30, 2026 — a functional, polished, demonstrable PWA must be ready.

## 2. Product scope and MVP priorities

The MVP focuses on, in rough priority order:

1. Libras alphabet (alfabeto manual).
2. Basic vocabulary (greetings, introductions, everyday expressions, family, numbers, common objects, basic questions).
3. Structured lessons (learning path → modules → lessons → exercises).
4. Visual learning materials.
5. Interactive exercises (multiple choice, image-to-answer association, vocabulary/alphabet recognition, Q&A).
6. User accounts and persisted learning progress.
7. Gamification (XP, streak, achievements, progress indicators).
8. Experimental camera-based practice.

Prioritize a complete, coherent learning journey over many incomplete features. A complete educational experience matters more than an unfinished advanced recognition system. Do not let the computer vision feature block the core platform.

## 3. Explicit product limitations — what Sinaliza is NOT

- NOT a universal Libras translator.
- NOT a complete sign language recognition system.
- NOT capable of understanding arbitrary Libras conversations.
- NOT a replacement for qualified Libras teachers or interpreters.
- NOT a system that understands facial expressions, body movements, grammar, or linguistic context.

Computer vision features must be presented honestly as **experimental learning assistance**. A successful geometric comparison does not mean a Libras sign was linguistically understood. Never present an experimental confidence score as linguistic accuracy, and never claim recognition capabilities that are not implemented.

## 6. Architecture conventions

- Each app under `apps/` is standalone and deployable independently (each maps to its own Vercel project with its Root Directory set to the app path).
- Next.js App Router: Server Components by default; Client Components only where interactivity requires them.
- Business logic lives in dedicated modules/services, separated from UI and persistence details.
- No separate backend service (no NestJS etc.): use Next.js server-side functionality + Supabase.
- Do not create `packages/shared/` or any shared package until code is *effectively* shared between applications. Do not create abstractions speculatively.
- Keep changes small and reviewable. Inspect existing code before changing it.

These conventions reflect the working direction recorded in `docs/decisions/` (ADRs 0001–0003), whose formal status is `Proposta — aguardando aprovação`. Treat them as binding unless the owner revises them; if an ADR changes on approval, update this file and the ADR together.

## 10. Database and Supabase conventions

- PostgreSQL via Supabase. Schema changes only through versioned migrations under `supabase/migrations/` — never ad-hoc dashboard edits that are not captured as migrations.
- Seed/development data under `supabase/seed/`.
- Keep business logic in modules/services, not scattered across route handlers.
- Table authorization differs by data kind (see §12): personal/progress data is isolated per user; educational content may allow public or authenticated read.

**API keys (current Supabase naming):** Supabase replaced the legacy `anon`/`service_role` JWT keys with a **publishable key** (`sb_publishable_...`) and **secret keys** (`sb_secret_...`). The legacy keys are being deprecated through the end of 2026 — prefer the new naming in all new code and docs. The publishable key carries the same low privileges as the legacy `anon` key (RLS still applies); secret keys replace `service_role` and bypass RLS entirely.

## 11. Authentication and security requirements

- Use Supabase Auth for registration, login, logout, and session persistence. Do not build custom auth.
- Protected routes must actually enforce authentication server-side, not only hide UI.
- Only the Supabase **publishable** key (`sb_publishable_...`) belongs in `NEXT_PUBLIC_*` variables. **Secret** keys (`sb_secret_...`, legacy `service_role`) must never reach browser/client code — no secret key may ever be exposed to the browser.
- Validate all user input; provide useful error messages.
- Never commit secrets, API keys, or credentials.

## 12. Row Level Security requirements

Differentiate policies by table kind — do not apply a generic ownership policy to every table:

- **Personal/progress data** (profiles, lesson completion, exercise results, XP, streak, achievements): RLS with policies scoped to `auth.uid()` — each user can only read and write their own rows. Test that a user cannot read or write another user's data.
- **Educational content** (learning paths, modules, lessons, exercises, signs, vocabulary): read access as the product requires — public read or authenticated-only read; writes restricted to admin/service contexts. Keep RLS enabled here too.
- Never bypass RLS with a secret key in application code.

## 13. Environment variable rules

- Secrets live in environment variables / `.env.local` (gitignored). Never in code, never in chat, never in commits.
- Maintain `.env.example` files with placeholder values documenting every required variable.
- Only `NEXT_PUBLIC_`-prefixed variables may reach the browser.

## 15. Accessibility requirements

Accessibility is a core product requirement, not a finishing step:

- Semantic HTML; full keyboard navigation; visible focus indicators.
- Adequate color contrast; accessible form labels; screen-reader-friendly feedback.
- Responsive layouts; `prefers-reduced-motion` support.
- Text alternatives for meaningful visual content.
- The educational experience must be fully usable **without camera access**. Never assume users can or want to use camera features.

## 16. PWA requirements

The `apps/pwa` application must be a Progressive Web App:

- Web app manifest, icons (reuse `sinaliza-icone-pwa.svg` / derived PNGs), installability, theme colors matching the palette.
- Service worker and a caching strategy with an offline fallback.
- **Priority:** PWA installability, app-shell caching, and access to previously cached learning content are the required offline baseline.
- **Conditional:** offline progress sync (preserve local progress, sync pending submissions on reconnect) is implemented only if it fits the deadline and can be tested safely — never at the expense of the core educational experience. Watch for duplicate progress submissions and conflicting updates.
- Do not promise offline functionality that is not implemented and tested.

## 17. Computer vision limitations

- Use MediaPipe in the browser; process camera input locally — do not upload camera footage to a backend.
- Scope: camera permission handling, preview, hand detection, 21-landmark extraction, coordinate normalization, geometric feature extraction, experimental comparison against validated reference examples, honest visual feedback.
- Handle: denied permissions, unsupported browsers, no hand detected, multiple hands, camera init failures, low-quality input, device performance limits.
- The Python PoC (`sinaliza-poc` repo) is the reference for which features to extract — do not assume the Python code itself can be reused in the browser. Verified files: `main.py` (real-time webcam loop), `feature_extractor.py` (seven geometric features over 21 normalized landmarks), `classifier.py` (exemplar-based Euclidean matching over `dataset.json`), dataset tooling (`analyze_dataset.py`, `convert_dataset.py`, `visualize_dataset.py`), tests (`test_environment.py`, `test_features.py`, `test_normalization.py`) and the `hand_landmarker.task` model. It classifies three static hand configurations (`aberta`, `punho`, `pinca`).
